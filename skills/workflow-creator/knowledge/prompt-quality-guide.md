# prompt-quality-guide.md — Writing High-Quality AI Workflow Prompt Files

This guide defines the standards for `.md` prompt files used by `ai-workflow-runner`. Step 03 loads this file before presenting any prompt suggestions. These principles also inform how Step 04 embeds quality comments into generated prompt files.

---

## Core Principles

### 1. Single Responsibility

Each prompt file handles exactly one focused task. It produces one clearly defined artifact.

**Wrong:** "Analyze the codebase, generate documentation, and create tests."
**Right:** "Generate API documentation for all public endpoints in `src/api/`. Output as a single Markdown file."

### 2. Explicit Objective

State the goal in one unambiguous sentence at the top. The AI must not have to infer what success looks like.

**Wrong:** "Help with the code analysis."
**Right:** "Analyze `src/` for all exported TypeScript interfaces and output a JSON object mapping each interface name to its file path."

### 3. Explicit Output Format

Specify the exact format the AI must use. If it's JSON, show the schema. If it's Markdown, show the structure. If it's a file, name it.

**Wrong:** "Return the results in a structured format."
**Right:**

```
Output MUST be valid JSON matching this schema:
{
  "interfaces": [
    { "name": "string", "file": "string", "methods": ["string"] }
  ]
}
Do not include any text outside the JSON object.
```

### 4. Explicit Constraints

List what the AI must NOT do, in addition to what it must do. Prevents scope creep and hallucination.

Examples:

- "Do not modify any source files."
- "Do not include private methods (prefixed with `_`)."
- "Output must not exceed 50 lines."
- "Do not reference external URLs."

### 5. Success Criteria

Define what a passing output looks like. This maps directly to the validation script's checks.

**Wrong:** "The output should be good quality."
**Right:**

```
SUCCESS CRITERIA:
- Output is valid JSON (parseable without error)
- Every entry has a non-empty "name" and "file" field
- "file" paths are relative to the repository root
- No duplicate "name" entries
```

### 6. Data Isolation

Each prompt file runs in a completely isolated environment — no memory of prior steps. If a step needs data from a previous step, it must be passed explicitly via `env_vars`.

**Wrong (assumes shared memory):** "Continue from where the previous step left off."
**Right:** "The previous step's output is available in the `PREV_STEP_RESULT` environment variable. Parse it as JSON to get the list of files to process."

### 7. Progressive Output — Scaffold Then Fill

The AI agent should never accumulate all its analysis in memory and write the output file at the very end. Instead, it follows a two-phase approach:

**Phase 1 — Scaffold:** Before starting any analysis, create (or open) the output file. For each required section, check whether it already has content. Only add a `<!-- PLACEHOLDER: ... -->` marker for sections that do not exist yet or are empty. Sections that already contain real content from a previous run are left untouched.

**Phase 2 — Fill progressively:** As each section's analysis completes, compare the new content against what is currently in the output file. If the section contains a placeholder, replace it with the real content. If the section already has content, update it only if the new content is different. Do not wait until all sections are complete.

This means the output file exists from the start of the step, transitions from skeleton to complete artifact, and always reflects the latest progress. A partial run leaves behind a mix of completed sections and placeholders — a subsequent run picks up from where it left off.

**Wrong (all-at-once):** Analyze everything, then write the complete file at the end.
**Right (progressive):**

1. Create `docs/api.md` with all headings — add `<!-- PLACEHOLDER: ... -->` only for sections that don't have content yet
2. As each API endpoint is analyzed, update the file — replace that section's placeholder (or update existing content if changed)
3. By the end, every placeholder is replaced with actual content

### 8. Step Boundary — Stop After Completion

Each prompt file represents exactly one step. The AI agent running the prompt has access to the full repository and may discover references to other steps, workflow files, or downstream tasks. Without an explicit stop instruction, the agent will often continue into the next step autonomously — wasting time, producing unrequested changes, and risking timeout.

Every prompt file MUST end with a clear stop boundary that tells the agent its work is done once this step's deliverables are complete.

**Wrong (no boundary):** Ending with just success criteria — the agent sees other step files and keeps going.
**Right:** Ending with an explicit completion instruction after the success criteria.

## Required Sections in Every Generated Prompt File

Every `.md` prompt file generated by this skill MUST include all seven sections:

```markdown
# [Step Name]

## Objective

[Single sentence describing exactly what this step must accomplish.]

## Context

[Any background the AI needs. Reference env vars if data is passed from previous steps.]

## Constraints

- [Constraint 1]
- [Constraint 2]
- [Add more as needed]

## Output Format

[Exact specification of the expected output. Include schema, structure, or example.]

## Progressive Output

Before starting analysis, create the output file (or open it if it already
exists). For each required section: if the section does not exist or is empty,
add a `<!-- PLACEHOLDER: [section description] -->` marker. If the section
already contains real content, leave it as-is.

Then, as each section's analysis completes, compare the result against the
current file content. Replace placeholder markers with the real content.
If a section already has content, update it only if the new content differs.
Do not wait until all analysis is done to write the file.

## Success Criteria

- [Criterion 1 — maps to validation check]
- [Criterion 2 — maps to validation check]
- The output file contains no remaining placeholder markers

## Completion

When the deliverables listed above are complete, STOP. Do NOT proceed to any
subsequent steps, do NOT look for or execute other workflow files, and do NOT
begin work that is not described in this prompt. Your task is finished when
the success criteria are met.
```

## Before/After Examples

### Weak Prompt (Do Not Generate)

```markdown
# Generate Documentation

Please analyze the code and generate documentation. Make sure it's comprehensive
and covers all the important parts. The output should be well-formatted markdown.
```

**Problems:**

- No clear scope ("the code" — which files?)
- No output format ("well-formatted markdown" — what structure?)
- No success criteria (what makes it "comprehensive"?)
- No constraints (how long? what to include/exclude?)

### Strong Prompt (Generate This)

````markdown
# Generate API Documentation

## Objective

Generate structured Markdown documentation for all TypeScript functions exported
from `src/api/` that are decorated with `@ApiEndpoint`.

## Context

No data is passed from previous steps. The source files are available in the
repository checkout at the standard workspace path.

## Constraints

- Only document functions with the `@ApiEndpoint` decorator
- Do not include internal helper functions
- Do not modify any source files
- Output must be a single Markdown file written to `docs/api.md`
- Do not include implementation details — document the interface only

## Output Format

A single Markdown file at `docs/api.md` with this structure:

```markdown
# API Reference

## [FunctionName]

**Route:** `[HTTP_METHOD] /path`
**Description:** [one-line description]
**Parameters:** [table of name, type, required, description]
**Returns:** [type and description]
```
````

Repeat for each endpoint, sorted alphabetically by function name.

## Progressive Output

1. First, scan `src/api/` to discover all functions with `@ApiEndpoint`
2. Create `docs/api.md` (or open it if it already exists) with the
   `# API Reference` heading and one `## [FunctionName]` section per
   discovered endpoint. For each section: if it does not exist or is empty,
   add `<!-- PLACEHOLDER: Documentation for [FunctionName] -->`. If it
   already contains real content, leave it as-is.
3. For each endpoint, analyze its signature and decorator metadata, then
   update `docs/api.md` — replace that endpoint's placeholder with the
   real Route, Description, Parameters, and Returns content. If the section
   already has content, update it only if the new content differs.

## Success Criteria

- `docs/api.md` exists after execution
- The file contains at least one `##` section
- Every section has a Route, Description, Parameters, and Returns subsection
- No placeholder markers (`<!-- PLACEHOLDER: ... -->`) remain in the output
- No placeholder text like "[TODO]" or "undefined" appears in the output

## Completion

When the deliverables listed above are complete, STOP. Do NOT proceed to any
subsequent steps, do NOT look for or execute other workflow files, and do NOT
begin work that is not described in this prompt. Your task is finished when
the success criteria are met.

```

## Guidance for Step 03: Suggesting Prompts

When generating a suggested prompt for a user's step, follow this process:

1. **Take the user's one-sentence objective** from Step 01 as the Objective section
2. **Identify inputs** — does this step receive data from a previous step? If so, note the env var name in Context
3. **Infer constraints** — what are the most common failure modes for this type of task? List them
4. **Specify output format** — if the user hasn't specified, ask or make a reasonable assumption and state it explicitly
5. **Write progressive output instructions** — describe the scaffold-then-fill approach: what placeholder structure to create first, and how to progressively replace placeholders as analysis completes each section
6. **Write success criteria** — derive from the output format; each criterion should be machine-checkable. Always include "No placeholder markers remain in the output" as a criterion

When presenting the suggestion, always remind the user:
> "Each prompt file runs in complete isolation — no shared memory between steps. If this step needs data from a previous step, it must be passed via `env_vars`."

## Chart and Visualization Steps

When a step generates charts or SVG visualizations, the prompt must include
specific rendering instructions. Load `knowledge/chart-rendering-guide.md` for
the full conventions. Key points:

- Use **Mermaid `xychart-beta`** for X-Y charts (line, bar) — not PlantUML
  (which has no native X-Y chart support)
- Render via `npx --yes @mermaid-js/mermaid-cli@latest` (do not add `mmdc` arg)
- Match chart width to other SVGs in the same output via a mermaid config file
- Post-process rendered SVGs: replace `width="100%"` with fixed pixel width

## Validation Script Alignment

A validation script should check the success criteria mechanically:

| Success Criterion | Validation Script Check |
| ----------------- | ----------------------- |
| "Output is valid JSON" | `json.loads(message)` — catch and report `JSONDecodeError` |
| "File X exists" | `os.path.exists('X')` — report if missing |
| "Contains required fields A, B, C" | Check each key in parsed JSON, report missing ones |
| "No placeholder text" | String search for `[TODO]`, `undefined`, `null` literals |
| "No placeholder markers remain" | Search for `<!-- PLACEHOLDER:` in the output file — report remaining sections |
| "At least N entries" | Check `len(data['items']) >= N` |

Each criterion in the prompt's Success Criteria section should map to a concrete check in the validation script. If a criterion is not machine-checkable, it should be rewritten to be checkable.
```
